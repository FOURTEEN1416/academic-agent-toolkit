# 技术路线图质量规范

仅在绘制 `fig_roadmap*`、`fig_technical_route*` 或承担“整篇研究路线总览”职责的图时读取本文件。它约束的是技术路线图，不应机械套用到数据图、机理示意图或算法细节图。

## 1. 先决定是否真的需要路线图

路线图回答五件事：输入是什么、共享的数学内核是什么、各子问题怎样继承/分支/汇合、每问发生了哪项关键数学变换、最终得到什么。它不是论文目录、模型公式汇编、参数表、结果摘要或质量检查清单。

如果一张图必须同时讲清每个子问题的完整公式、算法步骤、结果数值和验证方式，说明抽象层级混杂。保留信息充分的路线图，把模型机理或求解器内部结构另画一张架构图；不要把所有信息压进一个矩阵。反过来，路线图若只剩“输入→问题一/二/三→输出”，读者看不出实际数学工作，也属于不合格。

### 路线图不是“阶段 + 方法/工具”清单

禁止固定生成“阶段｜方法/工具”“问题｜模型｜求解｜验证”这类旁栏或满矩阵。它会把任何题目都压成同一种项目管理模板，而且读者看到的是分类标签，不是推理关系。

- **不是禁止方法，而是禁止方法分类栏。**实际模型、判据和求解转换应写进它所服务的语义节点，例如“定长弦递推整链”“患者级删失时间建模”；不能单独列一个泛化“方法/工具”栏。
- 软件名、编程语言、通用动作（数据清洗、结果分析、灵敏度分析）通常不进入总路线图。
- 路线图节点优先写“对象发生了什么变化”或“上一问为下一问提供了什么”，例如“碰撞临界时刻 → 最小螺距反演”。
- 题目各问并非独立时，必须把继承、扩展、分支或汇合画出来；不得简单竖排四个“问题一～问题四”。

### 信息充分性：不要为了防密集而画成提纲

- 每个核心节点采用“短标题 + 1～3 条题目特有的关键变换”。例如不能只写“问题二　碰撞分析”，应写成“首次碰撞｜矩形外轮廓间隙｜粗筛临界区间｜连续求根”。
- 输入节点交代真正决定模型的几何、数据或边界条件；共享内核交代可被各问复用的状态表示和递推关系；输出节点只交代待输出的量或结论类别，不抄最终数值，也不写“验证通过、结论成立、显著优于”等宣告式结论。
- 读者只看图，应能复述“上一问给下一问提供了什么、下一问新增了什么”。若不能，就优先补关键变换，而不是增加装饰、颜色或泛化阶段名。
- 一张路线图放不下求解器内部模块时，采用“路线总览 + 求解架构”两图配套。第二张图必须来自真实调用关系，例如构型递推器、速度传播器、碰撞判定器及其反馈调用；不得凭空生成软件分层图。

## 2. 语义骨架优先，禁止固定模板

先按真实依赖选择骨架，再在等价表达中使用稳定种子选择变体：

| 内容关系 | 优先骨架 | 等价变体 |
|---|---|---|
| 线性阶段推进 | 单主干 DAG | 上下、左右、轻微阶梯 |
| 一份数据支撑多个子问题 | 基座扇出—分支—汇合 | 中轴双侧、树状分支 |
| 多源输入共同支撑模型 | 多输入汇聚—主干—输出 | 分层汇聚、漏斗式汇聚 |
| 并行研究线最后综合 | 2–3 泳道并行—汇合 | 横向泳道、纵向泳道 |
| 真正存在迭代反馈 | 主干 + 一条明确回边 | 局部回边、末端回源 |

只有当“行×列”的比较关系本身就是论文结论时才使用矩阵。不能因为题目有多个小问就默认画“问题数 × 方法/求解/验证”的满矩阵。

同一篇论文统一字体、配色、圆角和线型；不同项目的骨架由数据依赖、阶段数、分支数、汇合方式和反馈关系决定。**配色严格服从用户选择**：选择黑白就全图零彩色，选择朴素/现代就保持对应色系；不得在生成时跨色系随机。不得用随机颜色代替结构差异，也不得为了差异化捏造分支或循环。

推荐的内容语法是：`研究对象/输入 → 共享数学内核 → 真实子问题关系 → 综合输出`。其中任何一层都可以缺省、拆分或改向；它不是固定四层模板。若全文没有共享内核，就从真实分叉或时间依赖开始，不得硬造“统一模型”。

## 3. 自适应信息预算

路线图必须同时满足：

- 语义节点建议 8–16 个，硬上限 18 个；标题、图例和纯连接件不计。
- 节点允许“标题 + 1～3 条短说明”，中文建议 8–42 字；单节点超过 64 个可见字符时拆分或改写。
- 紧凑型总览建议 180–320 个可见字符；解释型总览建议 260–480 个；硬上限 560。不能把建议值误当成追求最少文字的目标。
- 主要节点可有 2～4 行，但每行只表达一个短语。公式只允许短符号或模型简称，禁止完整推导式、长参数串和结果数值。
- 全图最多一个主焦点。阶段标签、分组标题和普通节点不得同时使用粗边框、粗体和深底。

超过预算时按顺序处理：删除重复说明 → 将完整推导移到正文 → 合并同层同义节点 → 拆成总览图与求解架构图。低于建议区间且看不出建模内核时应补充题目特有的关键变换。缩小字号不是解决办法。

## 4. 视觉层级

- 普通节点使用浅底或白底、常规字重和细边框；不要把每个节点都做成卡片标题。
- 主焦点最多一个，可用一条强调色边、浅色底或编号徽标，不能叠加粗黑边、双线、黑底白字三种强调。
- 路线图禁止大面积纯黑填充。纯黑白风格也只允许黑色用于文字、连线和细边框，不允许黑色横幅或整块反色节点。
- 正常文本对背景对比度不低于 4.5:1；关键图形和必要边界对相邻背景不低于 3:1。颜色不得作为唯一语义载体，分支仍需箭头、线型或文字标签。
- 同类节点保持尺寸、字号、标签格式一致；不同抽象层级不要混在同一排。

## 5. 布局与连线

- 主阅读方向只能有一个。节点间距和层间距稳定；分组之间的留白应明显大于组内间距。
- 优先使用 flex/grid 或自动分层布局；相邻同层节点等距对齐。
- 连线优先短直线或正交线，避免穿过节点。分叉使用公共母线/waypoint 后再分支，减少重叠。
- 无真实反馈时不画回边；有反馈时通常只保留一条最重要的回边。
- 需要五个以上阶段时，使用“阶段竖排 + 阶段内 2–3 个并列节点”或拆图，禁止一行铺满，也禁止把所有节点竖成一根长条。

## 6. 必须提供的机器可读标记

根 `.fig` 添加 `data-mh-quality="roadmap-v2"`，并按用户选择添加 `data-mh-palette="mono|plain|modern"`。每个语义节点添加 `data-mh-node="true"`；唯一主焦点额外添加 `data-mh-focus="true"`。阶段标签可用 `data-mh-role="stage"`，输入/输出/验证可分别标记 `input`、`output`、`validation`。

这些标记只用于质量检查，不改变渲染。没有标记时检查器会回退到 `.node/.n/.c/.stage/.key/.focus/.base` 等常见类名，但新图不得依赖回退。

## 7. 最终门禁

`--norm-check` 对路线图执行硬检查：

- 节点/模块超过 18；
- 全图文字超过 560，或单节点超过 64 个可见字符；
- 主焦点超过 1；
- 出现任何黑底白字语义节点/黑色底座，或深色填充覆盖画布超过 8%；
- 粗边框节点超过全部语义节点的 20%；
- 正常文字对比度低于 4.5:1；
- `data-mh-palette="mono"` 时出现任何彩色文字、背景、边框、连线或图案；
- 最终插入论文后有效字号低于 7pt、图占正文区过高、存在溢出/重叠。

任何一项失败都必须回到 HTML 改结构。视觉模型超时、不可用或未返回结论只能记为“未审成”，不能覆盖确定性门禁，也不能写成 PASS。

## 8. 规范依据

- draw.io 的一致性规范强调 concise、clear、consistent，同类元素保持尺寸、样式、位置和标签一致，并明确建议一张图保持同一抽象层级：<https://www.drawio.com/docs/best-practice/consistent-diagrams/>
- draw.io 的布局与连接器文档说明应按关系选择 Flow/Tree/Organic 等布局，并通过正交连接、waypoint 和间距设置减少连接混乱：<https://www.drawio.com/docs/manual/layouts/>、<https://www.drawio.com/docs/manual/connectors/>
- Graphviz 的 `nodesep`、`ranksep`、`overlap` 和 `splines` 是节点净空、层间净空、去重叠和绕节点连线的确定性控制：<https://graphviz.org/docs/attrs/nodesep/>、<https://graphviz.org/docs/attrs/ranksep/>、<https://graphviz.org/docs/attrs/overlap/>、<https://graphviz.org/docs/attrs/splines/>
- W3C WCAG 2.2 要求常规文字至少 4.5:1 对比度，理解所需的非文本图形通常至少 3:1，且颜色不能作为唯一的信息表达：<https://www.w3.org/TR/WCAG22/>、<https://www.w3.org/WAI/WCAG22/understanding/non-text-contrast.html>、<https://www.w3.org/WAI/WCAG22/Understanding/use-of-color>
