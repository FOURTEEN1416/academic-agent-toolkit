# 专利技术交底书 · 起草阶段（patent-draft）

本步骤根据 `CLAUDE.md` 注入的**案件名称**和**技术描述/交底要点**，由 AI **直接撰写**一份完整的专利技术交底书草稿，输出到 `专利交底书/交底书草稿.md`；同时**自主设计**两张自包含 HTML 图（系统框图 `fig_arch.html` + 流程图 `fig_flow.html`）放到 `专利交底书/` 目录。下一步 `patent-build` 会把这两张 HTML 用 Electron 截成 PNG 并导出 Word。

## 场景与硬约束

- **两种输入模式，先判断当前属于哪种：**
  - **A. 用户上传了真实材料**：`CLAUDE.md` 会写明"用户已上传真实材料"，且 `user_data/` 下有文件（技术文档、设计说明、源代码等）。此时先用 `Glob`（**递归** `user_data/**`）/`Read` 通读这些材料——上传的压缩包已被后端**自动解压成子目录**，务必递归查找。**据实提炼**技术背景、要解决的技术问题、核心技术方案与创新点，写入交底书各章；技术方案、实施例、参数要与上传材料一致，`CLAUDE.md` 注入的技术描述仅作补充。
  - **B. 用户未上传材料**：`user_data/` 为空。此时按 `CLAUDE.md` 注入的案件名与技术描述，由 AI 直接撰写交底书。
- ⛔ 无论哪种模式，都**不要**调用 `docx_to_md.py`/`pptx_to_md.py`/`cnipa_epub_search.py` 等脚本（本工作流不提供它们）；模式 A 直接用 `Read` 读 `user_data/` 里的文本/代码即可。老 skill 里的 Step 1-8 分步 prompts 文件在工作区中**不存在**，不要 `Read prompts/*.md`；本文件已内联全部要点。
- **查新降级为 WebSearch**：需要现有技术对比时，用 WebSearch 检索相近专利/文献，理解其技术方案与局限，写入第一章。找不到可靠公开来源时，如实按技术常识概述现有技术方向，不虚构专利号和链接。
- **系统框图（3.2）与流程图（3.4）一律自主设计成自包含 HTML 图**（见下方《HTML 图设计规范》），产出 `专利交底书/fig_arch.html`、`专利交底书/fig_flow.html`；正文用注释 `<!-- ![系统框图](figures/fig_arch.png) -->` / `<!-- ![系统流程图](figures/fig_flow.png) -->` 占位引用（PNG 由下一步 patent-build 截图生成，此刻尚不存在）。⛔ 不要 ASCII 文字框图/箭头流程图，也不要再用 mermaid。
- 输出固定为 `专利交底书/交底书草稿.md`（单文件，不带时间戳后缀——时间戳命名是老 skill 的交付惯例，本工作流由 patent-build 统一导出 Word）。
- **正文止于第六章**。不得包含"自检清单"章节，不得在文末加入指向技能/示例仓库的脚注、免责声明或"教学示例"字样。
- 起草完成后，向用户简要汇报交底书要点，平台会触发一次人工检查点等待确认；确认后进入 patent-build 导出 Word。

## 章节结构（严格按此撰写）

```
文档头部（案件名称、技术联系人、专利类型、注意事项）
一、技术背景与现有技术
   1.1 现有技术（按技术方向分类；查新结果，WebSearch 来源）
   1.2 现有技术存在的缺点
二、本发明所要解决的技术问题
三、本发明技术方案的详细阐述
   3.1 背景
   3.2 系统框图（自主设计 HTML，注释占位引用 figures/fig_arch.png）
   3.3 模块功能说明（作用与关联关系，非输入输出）
   3.4 系统流程说明（自主设计 HTML 流程图，注释占位引用 figures/fig_flow.png + 文字说明）
   3.4.1 符号与公式（出现公式/形式化变量时必设；先符号定义，再公式）
   3.5 关键技术参数（参数表「符号」列与 3.4.1 同形）
四、与现有技术相比的优点
五、技术关键点和欲保护点
六、其它（实施例、技术效果、参数示例）
```

```markdown
**技术联系人**：

- 电话：[待填写]
- 邮箱：[待填写]

**专利类型**：发明

## 注意事项

（1）交底书应使代理人能看懂，尤其是背景技术和详细技术方案，一定要写得全面、清楚、完整；
（2）技术的公开程度，应以本领域普通技术人员不需付出创造性劳动即可进行实施为准。
（3）在与代理人沟通时，对于代理人咨询的技术问题，应给予回答并认真讲解，并按要求及时正确地补充相应技术材料。
```

`**案件名称**：` 行必须写实际案件名（CLAUDE.md 注入；未注入时据技术描述拟一个"一种……方法及系统"式名称）。

## HTML 图设计规范（3.2 系统框图 + 3.4 流程图各出一张）

本步只**自主设计并 Write 两张自包含 HTML**（`专利交底书/fig_arch.html`、`专利交底书/fig_flow.html`），**不出图**——PNG 由下一步 patent-build 用 Electron 截图生成。正文用注释占位引用（见上）。参考起点在工作区 `_templates/`（`tpl_arch.html`/`tpl_flow.html`/`themes.css`），但**不必照抄**，按下方规范从零设计更好。

**产物固定命名**（下一步截图按此对应）：系统框图→`fig_arch.html`（截成 `figures/fig_arch.png`）；流程图→`fig_flow.html`（截成 `figures/fig_flow.png`）。

### 硬约束（⛔ 违反即出图翻车）

1. **一路 `fit-content` 收缩到内容**：`html, body` 与最外层根容器 `.fig` 都写
   ```css
   html, body { margin:0; padding:0; width:fit-content; height:fit-content; background:transparent; }
   .fig { width:fit-content; height:fit-content; }
   ```
   ⛔ 根容器**禁**固定像素宽（`width:640px`）或 `100%/100vw`——否则截图会量到视口宽、右侧留大白边。留白靠内部 `padding`/`gap`。
2. **flex/grid 自动布局，禁 `position:absolute` 定坐标**：节点/连线/分区一律 flex/grid 排布——这是"永不重叠/错位/连线穿越"的根本。
3. **单文件自包含，禁外链**：CSS 内联在 `<style>`；不引 CDN、网络字体、外部图片；字体用系统栈 `"Microsoft YaHei","Noto Sans SC","Segoe UI",sans-serif`。
4. **画布透明**：`html`/`body`/`.fig` 背景一律 `transparent`，**整图不铺底色块**（近白 `#fff`/`#fafafa` 也不行），只有节点自身可浅填充。
5. **专利图内可含标题**（与竞赛不同——竞赛靠 LaTeX caption，专利 Word 里图上方可保留一行图名/小标题；也可不放，交由 patent-build 的"图 N"题注）。
6. **单页，宽高比 ≤ 8:1**：内容多时优先增高不增宽或分区换行。
7. **禁 emoji、禁装饰图标字体；节点文字禁写任何 LaTeX 排版命令**（`\small`/`\textbf`/`\node` 等会原样显示成乱字）。含公式时用 `\(...\)`/`\[...\]` 包裹，下一步出图加 `--render-math` 由 KaTeX 渲染。

### 结构忠实于逻辑（反"通用空壳"）

**结构服务逻辑，不为花样而花样**：线性方案画线性主干，有条件分支画分叉，有迭代/收敛画循环回流，多模块并行画分叉汇合，分层系统画分层堆叠。设计前先用一句话说清这张图的逻辑流向，再选最贴合的布局范式。

⛔ **严禁通用空壳**：节点全是万能词（`数据采集→数据预处理→建立模型→模型求解→结果输出`）的图信息量≈0，一律返工。每张图必须：
- **节点承载本专利特有的实体**：填真实的模块名/算法/判据/关键变量，让内行一眼认出"这是在解这个技术问题、用的是这套方案"。❌`建立模型`→✅`时变负载下的 (s,S) 补货策略`；❌`数据预处理`→✅`3σ 剔除异常+样条插补`。
- **挖出方案真实的非平凡结构**：参数标定回调、条件分支、收敛回环、多方法比选等真实存在的结构挖出来画上（只画真实存在的，不为"显深"编造）。
- ⛔ **脱敏**：业务/行业名抽象为通用描述，具体标签写"分类A/B/C"，公司/产品名删除或写"某系统"（与正文脱敏口径一致）。

**内核自检**：遮住案件名只看节点文字，能认出这是哪类技术、哪套方案吗？认不出=太泛，回去填实体、挖结构。

### 配色与造型（低饱和、克制、高级）

- **配色**：选一个主色相 H（0–359，避开刺眼黄绿[50,70)与高纯红），按 HSL 推导整套 `:root` 变量——主色 `hsl(H,38%,54%)`（只用于细边框/箭头/文字）、节点浅底 `hsl(H,20%,96%)`、分区底 `hsl(H,22%,92%)`、正文字 `hsl(H,14%,22%)`（非纯黑）、连线 `hsl(H,18%,62%)`。**两张图共用同一 H**，视觉统一。
- ⛔ **饱和度整体 ≤ 45%**；大面积填充**亮度 ≥ 60%**（浅底）；深色（主色及更深）只用于细边框/箭头/文字，**禁做大块实心填充**；有意义的颜色 ≤ 4 种；主文字对比度 ≥ 7:1。
- **造型**：圆角统一（6px 或 8px）、边框 0.75–1.5px 用连线色（禁粗黑边）、阴影克制（≤`0 1px 3px rgba(0,0,0,0.06)`）、节点内 `padding`≥10–16px、节点间 `gap`≥14–20px。
- **高级感五条**：①层次靠字重+留白+深浅不靠多色（主节点 `font-weight:700`）②连线语义化（回流用虚线+点缀色，双向流写清上行/下行）③每个节点主标题下加一行 `.sub`（10–11px、弱文字色）写方法细节/参数④同层级节点等宽等高、对齐整齐⑤全图只留一个焦点（柔和浅填充 `hsl(H,28%,84%)`+更粗边+更重字，不用实心深块+白字）。
- **反面清单（出现即返工）**：高饱和原色、粗黑边、大面积渐变、彩虹配色、emoji、多种圆角混用。

### 出图后（下一步 patent-build）会做什么

patent-build 会 glob `专利交底书/fig_*.html`→逐张 Electron 截 PNG（先几何自检报「文字溢出/越界/重叠」）→按注释占位把 PNG 嵌进 Word。**本步只保证 HTML 设计到位**；几何问题的自修复循环在 patent-build。

## 符号与公式体例（出现公式时必遵）

> **⚠️ 本节是撰写规范，仅供你遵循，严禁把规范条款文字（如"行内公式全文统一…不混用""禁止用上标表示维度"等）抄进交底书正文。** 正文只应出现符合规范的**成品内容**（符号表、公式、说明），不得出现规范说明本身。

- **先写符号表**（符号、含义、下标含义、量纲/取值范围），再写公式；式中符号与符号表同形同义。
- **禁止同一字母多义**。资源维度/类型标签（cpu、mem 等）写入**下标**并用正体 `\mathrm{cpu}`，如 `b_{i,\mathrm{cpu}}`；**禁止**用上标 `^{cpu}` 表示维度。
- 行内公式全文统一 `\(...\)` 或 `$...$` 二选一；块级公式统一 `\[...\]` 或 `$$...$$` 二选一，不混用。比较符用 `\leq`/`\geq`。块级公式尽量单行写完。
- 逻辑连接词（且/或）优先写在公式外的中文叙述里。
- 3.4.1 符号表、正文首次定义式、3.5「符号」列、第六章实施例四处逐字同形。

## 撰写要点

- 第一章每条现有技术尽量给出可核验的公开来源（WebSearch 得到的专利号/文献 + URL）；无可靠来源时如实按技术方向概述，不编造专利号和链接。
- 第三章是核心，要写全、写清，让代理人不需创造性劳动即可实施。3.3 聚焦模块作用与关联关系。
- 第五章列核心创新点，详细方案引用第三章（如"具体实现见 3.4.1"），避免大段重复。
- 第六章实施例的参数示例注明"不作为权利要求限制"。
- 全文脱敏、口径一致、公式符号跨节同形。
