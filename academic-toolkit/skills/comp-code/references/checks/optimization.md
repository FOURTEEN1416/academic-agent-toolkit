# optimization.md — 优化类自检（调度/选址/路径/分配/规划/求最优值）

> 目标：确认最优解真的可行、真的最优、且所有进正文对比的方案过同一套审计。
> 配套手册：`skills/_utils/error_prevention.md` 一章（优化类）+ 九章（约束闭环校验，含 constraint_audit.py 通用模板）。

## 1. 约束闭环审计（constraint_audit.py，写 RESULTS.md 前必做）

- [ ] 按九章 9.3 模板写 constraint_audit.py：**从最终写入的 results.json 重新计算所有约束**，不信任优化器输出的 constraints_ok 字段；
- [ ] 只输出结论（PASS/FAIL、n_violations、max_error、≤5 条越界定位），规则 B；
- [ ] **基线自动登记**：脚本开头扫描 results.json 键名，凡含 `baseline / naive / greedy / 就近 / 等权 / 均分 / 不调整 / lower_bound / 下界` 的方案自动进"待审基线清单"，断言每个都进了本次审计，漏审直接 FAIL；
- [ ] **基线同审**：每个进正文对比的对照方案，过与最优解完全同一套审计。两种合法结局二选一：① 基线也满足全部硬约束（正常对比）；② 基线不满足硬约束 → 结果里必须显式标注 `infeasible` 并说明其对比意义（如"仅作为无约束下界"）。禁止第三种（基线违规却不标注、直接进对比表）；
- [ ] RESULTS.md 末尾留 `<!-- AUDIT_OK source=results.json rechecked_at=<timestamp> n_constraints=K -->`。

## 2. 求解分层验证（由浅入深确认解的可信度）

1. **可行解存在性**：任何求解器运行前，先构造/验证至少一个可行解（贪心或全默认方案），否则模型本身可能 infeasible 而被误判为求解失败；
2. **求解状态与完成度**：status=Optimal；使用启发式/启发式时限时，声明 gap（mip_gap）与限时参数；
3. **目标值合理性区间**：目标值与下界/上界（题面推断或松弛解）对照，不出现"总收益超过资源总量上限"式荒谬；
4. **与基线对比方向合理**：优化解 ≥（max 型）/ ≤（min 型）全部基线，违反即排查（常见根因：基线过了约束而"最优解"没过，或目标函数方向写反）；
5. **解的结构性验证**（不是只看目标值）：
   - 抽 1~2 个决策实体（某车/某站点/某天）手工追踪完整方案，核对其满足全部相关约束；
   - 约束活跃性分析（error_prevention 一章 159 行起）：识别紧约束/松约束，紧约束与直觉一致，全松 → 目标函数可能写错方向；
   - 对偶量/影子价格（若可得）：稀缺资源的价格为正、冗余资源为零。

## 3. 结构合理性补充

- [ ] 解不违反物理常识：路径时段无时空矛盾（同一车同时出现在两地）、负荷不超载、排班不连班；
- [ ] 多方案对比时各方案使用同一数据、同一约束口径（防止"基线用旧数据、最优用新数据"式不公平对比）；
- [ ] 灵敏度：对 1~2 个关键参数做 ±10% 扰动，最优结构不发生脆变（或脆变有解释）。

## 4. 任务对齐硬断言

## modex-3 增补块（2026-09-10 同源对照吸收）

> 来源：Modex v3 技能包 comp-code/references/checks/optimization.md（溯源见 skills/shared-scripts/UPSTREAM.md）。
> 以下为本仓原版未覆盖的检查条目与可执行代码模板；条目与本仓上方重叠时，以本仓上方（含 validate_capability / AUDIT_OK 契约衔接）为准。

适用于调度、布局、选址、路径、分配等优化问题。验证题设要求与真实解，不要求所有题套同一种优化器、调参次数或容差。

## 1. 先定义正确性，再决定搜索预算

从题目与已确认模型列出变量域、硬约束、目标及单位。验证器从保存的完整解重新计算，而不是相信求解器返回的 feasible 字段。数值容差来自单位、离散精度或稳定性分析，先于结果确定；不能为了某次结果过关而放宽。

以下是阻断项：
- 违反题设硬约束、越界、非法变量类型或无法重新计算目标；
- 本应为有限值的计算结果出现 NaN/Inf；
- 输入来源错误、结果缺少必要字段，或声称的方法没有实现；
- 题目明确要求最优性证明或精度证据，但当前证据不足。此时标记未完成，不能伪称通过。

以下现象本身不是错误，只能提示核对：
- 解位于全部变量边界、资源未全部用尽、约束不活跃；
- 不同算例四舍五入后目标值相同；
- 某个算法没有优于基线、不同随机种子或不同启发式算法结果不相同；
- 到达时间/迭代预算，只有可行解而没有全局最优证明。

核对后发现真实违约才修模型/代码。不要为了消除上述现象，额外添加题设没有的约束、强制改数字或删除真实结果。

## 2. 选择与模型匹配的求解路线

- 线性/混合整数模型可以使用相应求解器；记录退出状态、原始/对偶界、gap 与实际采用的容差。
- 非线性、组合或多目标模型按已确认路线求解；不能把一般非线性求解器的 success=True 当作全局最优证明。
- 启发式先取得经过验证的可行解，再在有界预算内改进。只有可行解参与“最好结果”选择；若第一次试探不可行，不能把其目标值设成当前最优而拒绝后续可行解。
- 题目或建模方案未要求穷举调参时，不自动展开参数网格，也不固定重复五次。复用已有收敛曲线与独立运行结果，按剩余不确定性选择必要验证。

## 3. 交叉检查的数学含义

两个启发式给出不同结果，先分别检查解的可行性、目标复算、单位和预算，再比较收敛性。不能凭固定的 1 个网格、0.5% 或 1% 差异阈值断言其中一个必错。

若比较的是应当等价的解析实现，则按理论误差界和数值精度核对，超出误差界必须修复；不要把真实实现差错降为警告。

最小化问题的可行解提供上界，合法松弛等提供下界；缺少可验证下界时 gap 留空并说明原因。两次启发式目标的差异不是最优性 gap。

启发式没有找到可行解，只能记为“本次搜索未找到”，不是“证明不可行”。用二分缩小可行域时，只有可靠不可行证明才能更新不可行一侧；否则保留未知区间，改变求解策略或诚实报告未认证边界。

基线可以优于新方法，也可以有相同结果。不得通过 assert proposed_better 阻止保存真实基线比较；若论文声称改进，就修正声称或在预算内改进算法，不能修改数据。

## 4. 时间预算与断点

求解、交叉验证、调参和稳定性检查共享本问预算，不能每一层各自重新获得完整预算。先用代表性小规模样例估算成本，再选择合理上限（可按 5/10/30 分钟等量级调整，单次最长 1 小时）。长运行有可用进展时等待，不仅因超过几分钟就重写。

- 每个算例、种子或可复用子任务完成后，验证并使用 _utils/compute_checkpoint.py 原子保存。
- 保存输入、求解/公共/验证代码的哈希，参数、随机种子、库版本、验证状态；恢复时重新核对便宜的正确性检查。
- 当前算例失败只恢复该算例及受影响依赖；更改公共代码后相关检查点必须失效。
- 比较或稳定性分析优先用已保存的独立运行，不重复启动已有任务。需要新运行时计入原预算。
- 达到预算保存最好可行解及未完成事项；不删硬检查、不伪造证明、不无限追加重试。
- 前台执行；工具自动转后台后等待同一任务的最终回执，不能 end_turn 后期待唤醒。

## 5. 结构诊断与报告

约束活跃性、变量边界、闲置资源属于解释线索，不是“伪最优”证据。线性规划的角点最优、无须使用全部资源的最优解都可能合理。

随机稳定性报告应注明实际种子、样本数、目标与可行率；不能吞掉失败运行后只统计成功样本。均值接近零时 CV 不稳定，应报告绝对离散程度。若已有运行足够，不另外固定跑五个种子。

每问至少记录：
- 输入/模型与代码来源，实际执行的方法、参数、种子；
- 真实解及目标复算，硬约束验证结果；
- 求解状态、耗时、实际运行次数；近似/未认证/受限结论明确标识；
- 有证据时才填写上下界与最优性 gap；
- 实际做过的收敛、基线、敏感性或独立复核结果，不做则不声称。

完整结果文件只能在所有必需算例完成后汇总；失败情况下保留已验证检查点和准确的未完成说明，不把部分结果标为全部完成。
